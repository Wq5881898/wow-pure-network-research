# 机制 · 位置与坐标的权威性

> **本轮三次踩坑的共同根源。** 坐标有三个来源，只有两个可信。

## 三个来源，可信度不同

| 来源 | 是什么 | 可信？ |
|---|---|---|
| **服务端不回广播自身移动** | 会话内 `observed_position` / `current_position` **恒为登录点** | ❌ **整场会话都是过期的** |
| **桥接返回的 `submittedPosition`** | 桥接自己跟踪的角色位置，走完路径后更新 | ✅ **角色位置的唯一权威** |
| **目标生物的位置** | 可见对象里的 `movement.position_xyzo`（**静态 = 出生点**）与 `server_motion`（**外推，会跳**） | ⚠️ **出生点可信，外推不可信** |

## 规则

1. **凡涉及"角色在哪"，一律用桥接的 `submittedPosition`**（`agent_wow_session.submitted_position`）。
   用 `observed_position` 会得到"角色从没动过"的结论 —— 这正是 esc010/013/014/022
   一连串失败的根源。
2. **凡涉及"目标在哪"，先用刷新的对象**：世界状态**每次更新都替换对象**，
   `select_target` 存下的那个是**陈旧快照**，它的外推路径会跳
   → 同一瞬间两次测量可差 **8.4 码**（b8_u1）。
   修法：`PureNetworkBackend._refresh_target()`，在估位置前先换成活对象。
3. **同一次判断只测一次**：位置估计是**按时间外推**的，
   接近阶段与战斗前置各测一次会给出不同结果（b7_u1：接近测得 0.16 码、
   战斗测得 >5 码 → 拒绝开战）。
   修法：**共享快照** —— 测一次、两次都用同一份（`fight(target_position=...)`）。
4. **怪的出生点用静态字段**：`movement.position_xyzo` 不会被改写
   （实测同一 guid 的 62 条记录里一直相同）。脱战判定要用它，见 [[机制-脱战-leash]]。

## 目标的活体位置够用吗？—— 够

离线实测（b3_u1 / b4_u1 / huntL 三个抓包）：

| 量 | b3_u1 | b4_u1 | huntL |
|---|---:|---:|---:|
| 出生点→活体位置 中位漂移 | 0.8 | 2.5 | 5.0 码 |
| p90 漂移 | 11.0 | 8.9 | 12.3 码 |
| **落在出生点 15 码内的比例** | **99%** | **98%** | **99%** |

⇒ 活体位置 **98–99% 落在出生点 15 码内**（= 仇恨范围 20 码内）。
**位置精度不是问题**；问题是**用了陈旧对象**和**测了两次**。

## 🔴 位置分叉：桥接把"路径终点"当成了真实位置（2026-11-01）

**现象**（用户监控发现 ✓）：**角色卡在建筑物里、一直往前走** ✓ —— 撤离路线穿过了建筑 ✓。

**根因（代码确认 ✓）**：

| 位置 | 原行为 | 问题 |
|---|---|---|
| `probes/AgentWowBridge/main.go`（0x236 包 ✓） | `b.position` = **服务器报的位置** ✓ | ✅ 本来是对的 ✓ |
| `probes/AgentWowBridge/actions.go`（FollowPath 结尾 ✓） | `b.position = p`（**路径终点**）✗ | ❌ **用"我让它走到哪"覆盖了"它实际到哪"** ✗ |

**⇒ ⇒ 完整链条** ✓：
服务器有碰撞 ⇒ 角色被挡在墙/建筑里（**到不了路径终点** ✓）⇒
桥接却把终点记成它的位置 ✓ ⇒ **两边位置分叉** ✓ ⇒
之后所有规划（尤其**撤离** ✓）都从**假位置**出发 ✓ ⇒
路线从"墙里"开始 ⇒ 穿过建筑物 ⇒ **角色在建筑里一直往前走** ✓ ⇒ 逃不掉 ✓ ⇒ 死 ✓。

**⇒ ⇒ 为什么之前查不出来 ✓**：**报告里的位置全是桥接自己算的** ✓ ——
我拿一把坏尺子量了半小时 ✓ ⇒ **教训：先修测量工具，再用它做判断** ✓。

**⇒ ⇒ 修法（治本 ✓，已实装 ✓）**：
1. **桥接优先采用服务器的位置** ✓ —— 移动期间若收到过 0x236 ✓
   （用 `serverPositionSeq > startSeq` 判定 ✓）就用它 ✓，否则才回退到路径终点 ✓；
2. 桥接新增 `serverPosition` / `serverPositionValid` / `startSeq` ✓ 三个字段 ✓，
   `SubmittedPosition` 也改成返回**确认过的位置** ✓。

**⇒ ⇒ 后续可做（还没做 ✓）**：
- **卡住检测** ✓：位置没变但时间在走 ⇒ 判定卡住 ⇒ 放弃该路线 ✓（现在要靠人看屏幕 ✗）；
- **规划前校验起点偏差** ✓：桥接位置与服务器位置差 >15 码 ⇒ 重新规划 ✓。
