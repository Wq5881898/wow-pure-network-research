# 脱离战斗机制：实机测量与对档案结论的更正

本文档先用存档实测提出假设，再用**实机测量推翻它**，给出最终的脱离协议。结论以实机为准。

## 一、假设（来自 46 个历史会话的离线实测）

对 379 个存档 trace 逐包重放，筛出角色曾进入 `in_combat=True` 的会话（去重 46 个）：

- 32 个在会话内清除了 `in_combat`，14 个没有。
- 清除延迟（以最后一次受伤为起点）：**中位数 1.34 s，最大 2.98 s**。
- 清除机制：26 个因**攻击者死亡**，其余因攻击者存活但停止攻击。
- 成功清除的 32 个会话中，**角色全程位置不变**。

据此提出假设：**停止攻击 → 目标不再攻击 → 仇恨在 1～3 秒内失效 → 可安全登出。**

这个假设在 2026-11-01 的实机测量中被**推翻**。

## 二、实机测量（esc003，真实服务器）

条件：Scorpid Worker（entry 3124，level 3，HP 71），距离 2.77 码；30 码内仅此一个敌对生物。

```
start_attack → 0.12 s 进入战斗
攻击窗口 11.1 s，目标 HP 71 → 32（存活）
stop_attack
等待 45 s，只观测，不攻击
```

结果：

| 指标 | 实测 |
|---|---|
| 战斗是否进入 | 是，0.12 s |
| 停止攻击后 `in_combat` 是否清除 | **否，45 s 内从未清除** |
| 停止攻击后是否仍在挨打 | **是，HP 108 → 39（损失 69）** |
| 血量底线触发 | 是，HP 39（底线 40） |
| 结局 | 会话被脚本 `finally` 拆除，角色死亡 |

逐包时间线（`agent_wow_bridge_esc003.packets.json`）：

```
ms=5570   in_combat=True  hp=106
ms=30306  in_combat=True  hp=73
ms=52932  in_combat=True  hp=39    ← 会话结束，仍在战斗中
```

**全程 `in_combat=True`，无一次 False。**

## 三、更正：档案结论被误读了

重新检查档案后发现：先前统计的"1～3 秒仇恨失效"**全部**发生在**目标已经停止攻击**之后（目标死亡，或目标自己不再打）。

- 在 23 个清除会话中，16 个的"最后一次掉血"发生在清除前 3 秒内——但那是**目标已停手后的余波**，不是"目标还在打却凭空失效"。
- 目标**持续攻击**的情形，档案里根本没有"清除"样本——因为那些会话都在清除前被拆掉了（cs002、long01_verify 等 11 个，可用时间中位数仅 0.54 s）。

**所以真相是：**

> `in_combat` 不会因为"我停止攻击"而自行清除。它在**目标停止攻击**之后才清除（典型是被击杀）。
> **被动等待不是通用的脱离手段**——它只在目标已经收手时有效。

这是我先前结论的错误。`docs/117` 中"停止攻击 → 等 1～3 秒 → 可登出"的协议**不足以应对持续攻击的目标**，必须更正。

## 四、真正的脱离手段

要脱离持续攻击的敌人，只有两条路：

### 路线 A：击杀目标（26/32 档案案例走这条）

`in_combat` 随目标死亡立即清除。**这是唯一在档案中被反复验证的脱离路径。**

### 路线 B：脱离目标的仇恨范围（离开其可达范围）

目标追不上 → 仇恨失效 → 清除。但当前工程**无法在会话内确认自身位置**：

- 服务端**不向移动者广播自身移动**（`docs/88`；`agent_wow_session.py:220` 恒为 `current_position_confirmed: False`）。
- 因此"我是否已跑出仇恨范围"**无法在会话内验证**，只能事后由新会话登录位置反推。

`agent_wow_escape_control.retreat()` 已经实现了这条路径的雏形：**反向走已提交的导航路线**（不做直线弦），这是唯一有几何依据的撤离方式——`docs/51` 已记录该方案的规划与代价。

### 已被历史证伪的做法

| 做法 | 后果 | 出处 |
|---|---|---|
| 战斗中主动登出 | 服务端拒绝，角色留在世界继续挨打 → 死亡 | `docs/34`、cs002 |
| 战斗中拆除会话 | 同上 | cs002（本次） |
| 停止攻击后干等 | 目标持续攻击则永不脱离，血量持续下降 | esc003（本次实测） |

## 五、修正后的脱离协议

```
战斗未决时（目标存活且仍在攻击）：
  1. 停止攻击（不重发）
  2. 血量底线判断：
     - 血量健康（> 50%）：执行路线 B——沿已提交路线的反向撤离，撤出仇恨范围
     - 血量偏低（≤ 50%）：**不要**继续交战，也不要站在原地等
       → 优先路线 A（击杀）或沿反向路线撤离
  3. 任何时候都不得在 in_combat=True 时拆除会话或主动登出
  4. 脱战后（in_combat=False）再登出
```

**关键约束**：`in_combat=True` 时**唯一安全的动作是停止攻击**，其余（登出、拆除会话）都会把角色留在世界里挨打。

## 六、已实装的代码与本轮新增

### 已实装（`scripts/agent_wow_exit_recovery.py`）

- `close_session()`：存活但仍在战斗 → 先 `resolve_combat_before_exit()` → 再登出；已死/幽灵 → 不登出并如实记录。
- `resolve_combat_before_exit()`：**先停自身攻击**，再观察，再撤离；**不发攻击/拾取**；**血量底线**（默认 25）触发即中止等待并如实报告"站在原地等仇恨失效"会把角色耗死。
- 结果记录 `cleared_reason`（`target_died` / `left_reach` / `server_cleared`）、`actions`、`requests`，使"击杀"与"撤出"不再混淆。

### 本轮据实机结果新增的认知（尚未实装）

- 纯等待在目标持续攻击时**无效**，因此 `resolve_combat_before_exit()` 的等待只应是**第一道**手段；真正的脱离必须接上**规划远离敌人的路线撤离**（`agent_wow_escape_control.retreat`）或**继续战斗至击杀**。**已实装并实机验证（esc015）**。
- 血量底线必须与"是否还打得过"联动，而不是一个固定值。**尚未实装**。
- 撤离路线规划失败时必须有明确备选，不能停在原地耗血。**尚未实装**。

## 七、本轮的两次事故（如实记录）

主控在本轮**造成两次角色死亡**：

1. **cs002**（上一轮）：退出路径因角色在战斗中而拒绝登出 → 会话强制拆除 → 死亡。已修（退出前先解决未决战斗状态），并已用独立重登确认恢复。
2. **esc003**（本轮）：**我写的实测脚本自身**在 `finally` 中无条件 `backend.close()`，即使角色仍在战斗中。血量底线正确触发（HP 39 时停止等待），但脚本随后仍拆除了会话 → 再次死亡。

**esc003 暴露的正是协议缺陷本身**：脚本"知道"角色还在战斗中（报告里明确写了 `logout: skipped, reason: still in combat; the session is deliberately NOT torn down`），但 `finally` 的无条件 `backend.close()` 出卖了这个决定。**任何会话管理代码都必须把"仍在战斗中"作为硬约束，而不能只依赖调用方的意图。**

角色已再次用墓地灵魂医者恢复，并经**独立重登**确认：HP 108/108、`ghost=False`、`in_combat=False`、12 类物品、任务 792 仍在（0/8）。

## 八、更正：esc008 的"验证成功"实为击杀（本轮推翻）

上一版本文把 esc008 记成"两阶段脱离协议在真实服务器上生效"。**那是错的。**
重新逐包解码后，esc008 的脱战原因不是撤离，而是**敌人被打死了**：

| 证据 | 值 |
|---|---|
| `CMSG_ATTACK` | ms=5504、6548 |
| `CMSG_ATTACKSTOP` | **ms=30967**（比攻击晚 24 秒） |
| 目标 3124 HP 轨迹 | 71→55→47→39→31→24→17→10→3→**0** |
| `in_combat` 清除 | ms=31003，与敌人死亡同一时刻 |
| `retreat_outcome` | `null`，且链路上**没有 `follow_path`** |

也就是说：所谓"8.823 s 脱战"，是**角色连续自动攻击 24 秒把敌人打死**的结果，
阶段2 的撤离**从未执行**（无 `outbound_route` 可用）。

**根因**：`resolve_combat_before_exit()` 的"被动观察"阶段**从不停止角色自己的攻击**，
所以它根本不是被动的 —— 角色一边"观察"一边在打。归档里那些"清除"的样本，
很可能有相当一部分是同样的机制：观察期间把敌人打死了。

**已实装的修正**：

1. 脱离分支**先发 `stop_attack`** 再观察（`actions` 记录实际动作）。
2. 结果**区分两种结局**：`target_died` / `left_reach` / `server_cleared`，
   击杀**不得**再被记成撤离成功。
3. 记录 `cleared_reason` 与目标实时 HP（`Observation.context['target_health']`，
   取自可见对象实时值而非选择时的快照）。

## 九、路线 B 的三个真实障碍与最终实机验证（esc010/esc013/esc014/esc015）

修好"先停攻击"之后，路线 B 才第一次被真正执行，随即暴露三个**独立**障碍。
每一次都导致角色死亡，如实记录：

| 运行 | 障碍 | 证据 | 修正 |
|---|---|---|---|
| **esc010** | 反向接近路线只有 **6 码**，撤不出去 | 接近仅提交 3 个路点；角色坐标全程未变；敌人持续攻击 45 s，HP 99→42 | 撤离路线改为**在 navmesh 上规划到远离敌人 45 码**的位置，而不是反向接近路线 |
| **esc013** | 敌方正后方是**悬崖**，路线被拒 | `plan_escape_route` 返回 `null`；`_densify` 抛"落差超过 5 码" | 撤离方向改为**扇形搜索 12 个方位**，取第一个可行走方向 |
| **esc014** | 路线起点用了**过期坐标**，桥接拒绝 | 起点为登录点（-634.6,-4296.0），首个路点距角色 87 码；桥接报"segment exceeds 15 yards" | 锚点改用**桥接自报的 `submittedPosition`**；路线按桥接限制（每段 ≤15 码、总长 ≤50 码）**分段下发** |

**关键机制（本轮才搞清楚）**：

- 服务端**不回广播移动者自身位置**（docs/88），因此会话内 `observed_position`
  恒为登录点；**唯一权威的自身位置是桥接每次路径后返回的 `submittedPosition`**。
- 桥接的路径校验是硬约束（`validatePath`）：**每段 ≤15 码且高差 ≤3 码、总长 ≤50 码**，
  违反即整条拒绝 —— 角色原地不动，正好留在仇恨范围内。
- 脱离需要的是**距离**，不是移动：反向一条 6 码的接近路线等于没撤。

**最终实机验证（esc015，决定性）**：

条件：Scorpid Worker（entry 3124，level 3，HP 71），走 42 点接近路线后交战。

| 指标 | 值 |
|---|---|
| 敌人 HP 轨迹 | 71→63→56→48→41→34→27→**19**（**始终存活**） |
| `CMSG_ATTACKSTOP` | ms=68670（撤离立即发出） |
| `in_combat` 清除 | ms=79678，此时敌人 HP **仍为 19** |
| `cleared_reason` | **`left_reach`**（撤出仇恨范围） |
| `retreat_outcome` | **`out_of_combat`** |
| 角色 HP | 108→77 |
| 独立重登复核 | **HP 108/108、存活、非幽灵、非战斗** |

**这次是真撤离，不是击杀** —— 这是路线 B 第一次被证实。

### 本轮共造成 3 次角色死亡

`esc010`、`esc013`、`esc014` 均由主控造成（每次都是路线规划失败导致角色留在原地挨打），
每次都用墓地灵魂医者复活并**独立重登**确认（HP 108/108 或 54/108、存活、非幽灵、非战斗）。
**每一次死亡都定位到了具体机制，并落成了代码修正和回归测试**，没有以"偶发"结案。

## 十、脱战方式的择优：击杀 vs 撤离（esc020–esc023）

路线 B 跑通之后，暴露出一个**次序错误**：脱战分支总是先撤离。
esc020 暴露了它的代价 —— 目标只剩 22/71 HP、角色还有 91/108 HP，却选择了撤离：
角色跑了 87 码、**吃了 60 点伤害**，战斗**仍未解除**，最终死亡。
**目标只剩一口气时，一刀就能结束战斗，逃反而是最贵的选择。**

于是脱战改为**择优**，判据全部来自实机：

| 情况 | 选择 | 依据 |
|---|---|---|
| 无可用撤离路线 | **继续战斗** | 站着不动挨打必死，打至少还有结束的可能（esc010/esc013/esc014） |
| 目标剩余血量 ≤ 其上限 35%，且角色血量比例 ≥ 50% | **击杀** | 一击结束，不必边跑边挨打（esc020） |
| 目标血量健康 | **撤离** | 逃跑的收益大于换血的代价 |
| 角色已在血量底线之下 | **两者都不做** | 低于底线不开启新的交战 |

### 两条路线都已在实机验证（角色存活）

| 运行 | 目标状态 | 选择 | 结果 |
|---|---|---|---|
| **esc021** | 满血 71/71 | 撤离 | `cleared_reason=left_reach`，**仅掉 3 点血**（108→105），13.8 s 脱战 |
| **esc023** | 残血 20/71 | 击杀 | `cleared_reason=target_died`，`fallback_outcome=target_dead`，6.4 s 脱战 |
| esc015 | 残血 19/71 | 撤离 | `cleared_reason=left_reach`，敌人存活于 19 HP，角色存活 |

esc021 是目前**最强的一次路线 B 证据**：目标是**满血**的，角色只掉 3 点血就脱战 ——
说明"撤出仇恨范围"确实生效，且代价远低于换血。

### 顺带修掉的第三个过期坐标缺陷

esc022 里判据选对了（目标 20/71 → 选择击杀），但**战斗没打起来**：
`fight()` 用 `current_position` 测距离，而那是**登录点**，离目标 87 码，
于是触发 `preconditions_not_met`（距离 > 5）直接放弃。
**距离测量必须用桥接自报的 `submittedPosition`** —— 与撤离路线锚点是同一个道理。
生产路径 `_do_fight` 的距离测量有同样问题，一并修正。

## 十一、脱战择优与状态机的对齐（2026-11-01 第 7 段）

前面第十节把"击杀还是撤离"的择优做进了**退出分支**。但状态机
（`agent_wow_combat_state_machine.py`）还在用旧语义，两边会漂：

- 状态机的 `escape_path_planned` **在生产接线里恒为 `False`**
  （`agent_wow_session._do_fight` 从不传值），
  所以 `request_escape` 分支**根本不可达**；
- 状态机在锁定后的低血退出里给出 `hold_and_observe` —— 正是我实测三次致死的
  **站着空等**。

**修法：两边共用一条规则。**
`agent_wow_combat_state_machine.choose_combat_ending()` 是唯一的规则：

| 情况 | 结果 |
|---|---|
| 没有可用撤离路线 | **继续战斗**（空等必死，战斗至少还有结束的可能） |
| 目标剩余血量 ≤ 其上限 35%，且角色血量比例 ≥ 50% | **击杀目标** |
| 角色已在血量底线之下 | **撤离**（不开启新的交战） |
| 其余 | **撤离** |

- 退出分支改为调用这条规则（`_combat_ending`），**删掉自己的副本**；
- 状态机的锁定分支改为调用同一条规则，**不再给出 `hold_and_observe`**；
- `ObservationView` 增加 `target_max_health`（加法），使目标剩余比例可用；
- 会话新增 `escape_route()`：**按目标缓存一次**撤离路线，
  状态机与退出分支拿到的是**同一条路线**（否则"记录的决策"与"执行的决策"会不一致）。

### 真实存档回放验证（esc020）

esc020 是真实战斗：角色 HP 91→31，目标剩 22/71。用回放工具驱动对齐后的状态机：

| `escape_path_planned` | 决策轨迹 |
|---|---|
| False | `precheck` → `in_combat/continue_attack` → **`low_health_exit/stop_attack`** → **`low_health_exit/continue_attack`** → `unresolved/abort_unit` |
| True | `precheck` → `in_combat/continue_attack` → **`low_health_exit/request_escape`** → `unresolved/abort_unit` |

**旧行为在同样的真实样本上是 `hold_and_observe`** —— 已经被这条回归守卫钉死
（`scripts/test_combat_ending_replay.py`，4 项，全部用真实存档）。

## 十二、强制接入：状态机开始真正否决派发（2026-11-01 第 8 段）

状态机此前只**记录**决策。现在它可以**否决**（`--enforce-state-machine`，默认关闭）。

### 会改变哪些分支（任务书 D 项要求列出的）

| 状态机决策 | 原行为 | 强制接入后 |
|---|---|---|
| 低血退出 `stop_attack` | 战斗**继续**（fight 自己的底线是 HP<25 的绝对值） | **在比例线（50%）停手**，交给恢复分支 |
| 目标离距 `stop_attack` | 继续追打（cs002 的成因） | 停止追击 |
| `request_escape` / `abort_unit` | 无对应动作 | 结束战斗，由恢复分支处理 |

**outcome 字符串没有新增** —— 沿用项目已经认识的：
低血 → `health_budget`（`settle` 早已对它做防御性持有），
离距 → `target_left_melee`，
放弃 → `budget_exhausted`。
所以 `wsl_task_runner` 的 `outcome=='target_dead'` 判据、
`agent_wow_batch` 与 `audit_task_unit_evidence` 的依赖都不受影响。

### 真实存档上的效果（esc020）

esc020 是真实战斗：角色 HP **91→31**，目标剩 22/71，角色**死了**。

| 阈值 | 触发时的 HP |
|---|---|
| fight 控制器自己的底线（绝对 `health<25`） | **从未触发**（最低只到 31） |
| 状态机的低血线（比例 `<50%`） | 触发（37%） |

也就是说：**没有强制接入时，这场战斗根本不会被血量停住**，会一直打到预算耗尽
——正是致命的模式。强制接入把停手点从"永远不到"提前到 37%。

守卫：`scripts/test_enforcement_real_samples.py`（2 项，用真实存档）、
`scripts/test_combat_enforcement.py`（5 项，机制）。

### 两会话单元的实机验收（enfm1 → enfc1，强制接入开启）

会话内无法确认自身移动（docs/55/88），真实战斗必须走**两会话边界**流程：

| 会话 | 内容 | 结果 |
|---|---|---|
| **enfm1**（movement-only） | 接近蝎群并登出 | 边界可用：`expected_xyz = (-707.53, -4348.38, 49.06)`，登出 closed |
| **enfc1**（verify + combat，`--enforce-state-machine`） | 新登录确认落点 → 单次战斗 | 战斗 `unknown`（outcome `target_left_melee`）→ **计划中断 → 恢复分支被派发并记录** → 角色 HP **108/108**、非战斗、正常登出 |

这次实机验收同时证明了三件事：

1. **强制接入开启后正常路径没有被破坏**（战斗照常发起、照常结束）；
2. **结构修复生效**：战斗以未知态结束时计划中断，
   **恢复分支仍然被派发**，并在证据里是一个已记录的动作
   （`recovery_branch.records = [('recover_combat','success',...)]`）；
3. **角色存活**（HP 108/108，非战斗）。

顺带修掉一个**真实缺陷**：`movement_boundary` 读的是 `finalize['status']`，
而运行器写的是 `finalize = {'status':'resolved','logout':{'status':'closed'}}`，
于是**新产生的 movement-only 运行无法作为边界**。现在边界校验读**实际登出状态**
（`finalize.logout.status`，兼容旧的 `finalize.status`）。

**仍未在实机上验证的**：强制接入的**否决路径**（低血线触发停手）。
本次战斗以 `target_left_melee` 结束（目标移出近战），没有走到低血线。

### 否决路径的实机验证（vetoC → vetoD）

先查清默认 50% 低血线在本机的**可达性**（用 esc010/013/020 的原始攻击事件算出）：

| 量 | 实测值 |
|---|---|
| 角色每次命中 | **7.0–7.7** 伤害（约 0.65 次/秒 → ~4.8 伤害/秒） |
| 3124 蝎群每次命中 | **2.2–2.9** 伤害（只有**一个**攻击者，蝎群不会一起仇恨） |
| 3124 蝎群被打死 | 71 HP ÷ 4.8 ≈ **15 秒** |
| 角色在这 15 秒里掉的血 | ≈ **42**（HP 108→66，**够不到 54**） |

**结论：角色在"还在打"的时候赢下伤害交换**，所以 50% 线**不会**在
一场打得赢的战斗里触发 —— 这正是它该有的行为。

**更正一处此前写错的断言**：先前写的"默认 50% 低血线在本机内容下不可达"
**是错的**，那是从"打赢"这一种情形推出来的。实测三次死亡里角色**都越过了 54**
（分别在 HP 53 / 52 / 53 时越过）—— 只不过**都是在角色已经停止攻击、
敌人还在打的那段时间里**。也就是说：

> 低血线**可达**，但它触发时伤害**已经基本造成了**。

**所以低血阈值不是那三次死亡的原因，也不是解药**：
真正起作用的是"有路可走"和"离开而不是站着"（这两条本轮已修并验证）。

level 4 的 11378/10556（86 HP）也试过 —— **它们根本不主动攻击**
（战斗全程 HP 108 未掉），本机没有"打得赢但会掉很多血"的目标。

因此把低血线**做成可配置**（任务书本来就要求"阈值配置化"），
用 `--low-health-ratio 0.9` 让它在本机可达，然后实机验证否决路径：

| 环节 | 实机证据（vetoD） |
|---|---|
| 状态机决策轨迹 | `precheck/start_attack`(HP 108) → `in_combat/continue_attack`(HP 106) → **`low_health_exit/request_escape`(HP 96, `enforced=True`)** |
| 战斗结局 | **`health_budget`**（沿用既有 outcome 契约，没有新增字符串） |
| 计划中断后 | **恢复分支被派发并记录**（`recover_combat: success`） |
| 恢复分支的结局 | `ending=escape`、`cleared_reason=left_reach`、`retreat_outcome=out_of_combat` |
| **独立重登复核** | **HP 108/108、存活、非幽灵、非战斗** |

**完整链条在真实服务器上跑通了**：状态机否决派发 → 战斗以既有 outcome 结束 →
计划中断 → 恢复分支独立执行 → 按共享规则选择撤离 → 沿规划路线撤出仇恨范围 →
角色存活。

**结论同时也是一条限制**：**默认的 50% 低血线在本机内容下几乎不会触发** ——
不是"不可达"，而是"只在角色已经停止攻击、敌人还在打的那段里才达到"。
保护角色的是"目标移出近战"与"恢复分支"这两条，
**低血退出是一条兜底，不是主力**。阈值可配置只是让机制可验证，
**不代表默认阈值需要改**。

### 低血阈值：项目方怎么定的，50% 合理吗

**项目方的依据**（不是我的判断）：

1. **任务书只要求"比例化 + 记录换算"，没有规定具体数值**：
   > 阈值配置化且**以 max_health 的比例表达**……禁止裸绝对血量比较；
   > **默认值需在报告中说明换算到 70/89/108 三种上限时的实际血量**。

2. **`0.5 / 0.25` 是 worker 选定的默认值，不是项目规定的**，并且已带换算表
   （`QWEN_COMBAT_STATE_001_交付报告` §5）：

   | max_health | 低血(50%) | 危急(25%) | 旧绝对 25 | 旧绝对 50 | 旧绝对 60 |
   |---|---|---|---|---|---|
   | 70（1 级） | <35 | <17.5 | 35.7% | 71.4% | 85.7% |
   | 89（2 级） | <44.5 | <22.25 | 28.1% | 56.2% | 67.4% |
   | 108（3 级） | <54 | <27 | 23.1% | 46.3% | 55.6% |

   报告给出的理由是**消除同一血量在不同等级下的语义漂移**：
   旧的 `health<50` 在 1 级是 71.4%（"几乎永远不满足"）、在 3 级是 46.3%；
   比例阈值下三档行为一致。**50% 落在那条漂移带的中段。**

3. **docs/76 明确把战术取舍留给用户**：
   > 补充控制器对低血目标移动、逃跑求援及距离增长的有界处置……
   > **保留需要用户决定的追击范围或战术取舍**。

**那么 50% 合理吗？调低是哪个方向？**

这里有个容易搞反的地方：**阈值是"低于它就退出"，所以调低 = 退得更晚 = 在敌人还在打的时候多挨一会儿**。
低血退出是一条**安全网**，安全网要起作用就得**早**，所以**调低是反方向**。

结合本机实测，可用区间大致是：

| 约束 | 数值 | 含义 |
|---|---|---|
| 下界（不能高于它） | **~61%** | 打赢一场战斗的最低血量（108→66）。高于此值会在**打得赢**的战斗里触发，**放弃击杀、丢任务计数** |
| 上界（不能低于它） | 0% | 显然 |

**50% 落在区间内，且偏向"早"的一侧** —— 在本机它几乎不会误触发，
在真正打不赢的战斗里又会比 `fight()` 自己的绝对底线（HP<25）早得多
（54 vs 25）。

**但要说清楚**：本机**没有"打得赢但会掉很多血"的目标**，
所以**无法用实机数据定出该在本机取多少**。50% 是**有依据的默认**
（比例化 + 换算表 + 落在可用区间内），不是拍脑袋，也**不需要因为本次测试而改**。
