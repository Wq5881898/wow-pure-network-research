# QWEN-COMBAT-STATE-002 验收与实机前置核查：状态机在真实战斗数据上暴露的两个致命缺陷

本文档记录 QWEN-COMBAT-STATE-002 的主控验收过程，以及在**实机受控验证**中发现并修复的两个阻断性缺陷。

## 一、背景：实机验证不能只跑"登录即脱战"

上一轮（`docs/114`）用**零游戏动作**的 login/poll/logout 只读会话验证了状态机：真实服务器上 `health_transmitted=True`，状态机走到 `disengaged_confirmed`，与服务器 `in_combat=False` 一致，单次采样不确认、停留时长门槛真实有效。

但那条路径**没有覆盖战斗中**。而"战斗恢复状态机"的核心价值恰恰在战斗中。因此本轮先做**离线**的真实战斗数据核查——用真实 long01 战斗存档逐包回放——确认状态机在真实战斗中的行为。

## 二、发现的两个致命缺陷（真实数据）

### 缺陷 1：pending start 被误当成"战斗已结束"，误报脱战确认

`fight()` 发出 `start_attack` 之后、服务器尚未置起 in_combat 标志的那段窗口里，采样是 `in_combat=False`。原实现在这段窗口里**打开了脱战确认窗口**，凑够 3 个连续采样 + 停留时长即判定 `disengaged_confirmed`。

真实 long01 存档上的实测：状态机在 **seq17**（服务器 seq29 才报 `in_combat=True`）就判定 `disengaged_confirmed`——**战斗还没开始就被确认"已脱战"**。

### 缺陷 2：`disengaged_confirmed` 是终态，无法复活

进入该终态后 `_finished=True`，此后任何采样只返回 `DECISION_NONE`，**再也回不到 `in_combat`**。

真实 long01 存档上的实测：整场 129 包真实战斗，状态机**从未**进入 `in_combat`、**从未**产出 `continue_attack`；128 个采样中 100 个是冻结的 `disengaged_confirmed`。

**后果**：若当时开启强制接入，这台角色会在**正在战斗**时被判定"已脱战"，进而可能放行登出或停止攻击——这是会致死的错误方向。两个缺陷叠加后，离线的 283 项测试**全部通过却没能发现它**，因为那些测试都用合成观测，没有一条用真实战斗的时间线。

## 三、修复

主控先写回归守卫 `scripts/test_combat_state_machine_pending_start.py`（3 项，在修复前**全部 FAIL**），再把修复委派给 Qwen。

Qwen 的修法（`scripts/agent_wow_combat_state_machine.py`，+91/-18）：

1. 新增 `_combat_observed` 标志，与 `_engaged` 分离。`_engaged` 只说明"攻击已建议/已派发"，**不说明"战斗曾发生"**。只有 `_combat_observed` 为真（即曾观察到 `in_combat=True`）才允许开启脱战确认窗口。
2. pending start 期间进入 `engaging` + `hold_and_observe`，不消耗任何确认预算。
3. `disengaged_confirmed` 不再是永久终态：后续确认的 `in_combat=True` 可使其复活并回到 `in_combat`/`continue_attack`。`dead`/`ghost`/`unresolved` 仍是真终态。
4. `low_health_exit` / `target_out_of_range` 的**单程 latch 语义不变**（低血/离距后不回战斗、不再 `start_attack`）。

新增 `scripts/replay_combat_state_machine_combat.py`（真实 long01 逐包回放，只读 `results/`）+ `scripts/test_combat_state_machine_combat_replay.py`。

## 五、主控自查出的一处探针缺陷（如实记录）

主控的**旧**对抗探针 `accept_sm.py` 有 3 项在新语义下报 FAIL。逐条核对后确认：**是我自己的断言写错了，不是回归**。

那 3 项断言的是"含掉血的窗口**永远不得**确认脱战"，但这条规则是在"停留时长按窗口起点累计"的**旧语义**下写的；修正后的正确语义是"停留时长由**当前这段连续干净样本**自己覆盖"。污染后干净段若自身跨满 2.0s，确认是**正确**行为。已用"污染后干净段 1.0s（< 停留时长）→ 不得确认"的对照用例证明真正的要求成立。

**教训**：连续多轮修正语义时，旧的探针文件本身成为过期断言的来源，必须随语义同步更新，不能只看它报红就判回归。

## 七、仍存在的限制

- **强制接入仍未启用**，状态机仍是默认关闭的建议式接入。

- 2.0 秒停留时长仍是未经实机标定的保守默认值。
- 修复后的状态机在**真实服务器**上尚未运行过；下一轮实机验证应同时采集 advisory 记录。
