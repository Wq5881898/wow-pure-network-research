## 4. 协议与状态的逐段契约

### 4.1 认证、realm 和 world

`auth/login.go`：版本 3.3.5、build 12340，平台线上字节 `68x\0`、系统 `niW\0`、locale `SUne`；账号及密码仅将 ASCII 小写转大写。用户名限 1–17 UTF-8 字节；密码非空。固定 SRP 群，B∈(0,N)，拒绝 u=0，随机 a，M2 常数时间比较。

`auth/srp.go` 的关键易错点是 40 字节 K 派生：32 字节小端 shared secret 的起始零字节跳过后对齐到偶数偏移；偶数/奇数字节分别 SHA-1，再交错。不能用普通 SRP 库的默认大端/填充规则替代。PIN/matrix/authenticator/custom integrity 不受支持。

`auth/realm.go`：ListRealms 使用保存 session 重连，realm 地址来自服务器列表，包含 flags、realm ID、可选 build。连接 authserver=127.0.0.1 不保证 realm world 地址也是回环；本项目此前 NAT 发夹问题须在列表层检查。

`worldconn/conn.go:107–175`：先收 40 字节挑战；摘要绑定账号、零 DWORD、client nonce、server seed、K；AUTH_SESSION 发送后初始化双向 header cipher 与独立 Warden 状态。认证响应可能是排队态；不是一帧 AUTH_OK 的固定脚本。

### 4.2 分帧与并发

下行普通头 4 字节（2 字节大端 size＋2 字节小端 opcode），扩展头 5 字节；上行头 6 字节（2 字节大端 size＋4 字节小端 opcode）。payload 不经 header cipher；Warden payload 另有 cipher。`ReadFull` 处理分片；size 最大 1 MiB；上行要求 len(payload)+4<10240。

会话一读协程、一 owner loop；写锁与 owner 负责顺序推进 cipher。取消后若已开始写入，动作结果可能未知；不得自动重试购买/提交/拾取等变更。Send 成功只能作为 written，不能作为 succeeded。

### 4.3 入场与退出

EnterWorld 重新列举角色确认 GUID 归属，移交连接后不能返回角色管理状态。ready 需同时收到 LOGIN_VERIFY_WORLD 和完成 TIME_SYNC_REQ/RESP。核心只记录会话状态，不解析完整对象属性。

ping 30 秒、pong 90 秒、写 10 秒、logout 30 秒。logout 准备按依赖逆序共享 5 秒预算；若服务端拒绝退出会 Resume 模块。断线后没有在此代码路径看到完整自动重登/重建世界状态逻辑，不能把能重连 auth 与 gameplay 自动恢复混为一谈。

跨地图的 NEW_WORLD/WORLDPORT_ACK、传送回执、移动速度确认等并非这份简短核心 handler 自动全部覆盖；必须审查 opcode 和服务端 handler 并纳入 gameplay controller。对“仅保持登录”与“跨地图完整客户端语义”分别验证。

## 5. 模块与 Python 桥：可落地的接口设计

上游模板仅 QueryTime/Status/OnPacket/BeforeLogout；QueryTime 发 CMSG_QUERY_TIME，OnPacket 要求 8 字节回复：前 4 字节 Unix time，后 4 字节到日常重置的秒数。不能假设是 4 字节。Status 返回缓存时间与 packet count，而非实时同步查询。

模块发现从 manifest＋descriptor 动态解析 unary gRPC；不支持任意 streaming 方法自动暴露。proto `bytes` 经 protojson 是 Base64；uint64 在 JSON 中通常为字符串。Python 桥的 GUID、seq、after 应保持整数精度，禁止以浮点绕一圈。

建议实现有界事件桥，而不是直接照抄缺少缓存语义的文章片段：

```text
OnPacket: 复制载荷 → 分配单调 seq → 有界环形缓存 → 迅速返回
Poll(after,limit): 返回 session_id、first_seq、last_seq、gap、packets
decoder: 解压/解码 → 带 source_seq/source_time 的世界状态
controller: 提交动作 → 等待具体成功/失败谓词
planner: 只读摘要、下达有界任务、改代码和恢复
```

须明确两个缓冲区：core→module 的 64 项队列，与桥 module→Python 的历史窗口。前者不能由增大 Poll 缓存解决；后者须有 gap 检测与重同步。初始快照不完整或 seq 有缺口时不能继续把状态当作完整。

Poll 响应还受 gRPC 消息大小及 JSON/Base64 膨胀影响；不能无限累计后一次返回。默认库限额需实际测量，报告不包含足够证据说明已解决。

分派失败策略：core 对 packet callback 出错 fail session，因此 OnPacket 不宜承担模型调用、编译、SQL 扫描或寻路。解析未知字段应记录并有界处理，不能只为保持在线吞掉所有损坏数据。

## 10. 和现有预研的并列关系

现有 `docs/17` 已有通过聊天命令选择自身和友方 NPC、addon 读出状态并落盘的运行记录；纯网络路线本次有核心构建与离线导航记录。二者当前证据覆盖面不同，不能直接按“成功/失败”排名。

共同可沉淀：任务/动作契约、状态时间戳、超时与失败分类、策略层、实验记录和回放。各自适配：addon API/保存时机/键鼠焦点 vs raw packet/增量字段/协议时序。视觉路线仍是另一类感知与执行候选。

服务端 widget/GM 观测可以做旁证：不作为普通协议客户端的输入，除非单独标为“服务端辅助路线”。SQL 公开静态世界知识与实时后台读写必须分开记录。多 Agent 阶段应明确研究的是编程能力、给定工具后的战略能力，还是协作能力，避免同时变化后无法归因。

3. 在 Linux 本地 Docker 下运行固定版本模板，时间查询至少关联请求前后的 packets_received 与 server_time，验证 hook 和清理。
4. 做有界 send/poll 桥，先录首批对象消息；完成 packed GUID/对象增量/压缩更新解析与缺口重建，再谈完整 world state。
5. 导航离线样本扩展；执行端先短距离移动/停止，用服务端状态或观察客户端旁证，处理高度与世界切换。
6. 单次施法/目标/拾取的成功、失败和未知结果，再连接固定区域任务控制器。
7. 两角色聊天与组队，先明确 seq、TTL、ready、ACK、超时；稳定后研究五 Agent 的自主协作与代码传播。
8. 对同一短场景测延迟、CPU/内存、动作效果、恢复和维护成本；模型费用按 cached/uncached/output 分开。

本清单是持续研究对象，不是要求择一或按失败永久排除路线。当前最值得复用的是已成型协议核心；最需要自己补齐的是可验证世界模型、受控运动执行和实验恢复。
