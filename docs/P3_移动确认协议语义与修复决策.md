# P3 移动确认协议语义与修复决策

## 已核实

本地 AzerothCore `src/server/game/Handlers/MovementHandler.cpp:344-395`：普通移动通过 ProcessMovementInfo 后，调用 `mover->SendMessageToSet(&data, _player)`。`Entities/Object/Object.cpp:2124-2127` 的重载将该玩家作为 skipped_rcvr 传给广播分发器。普通移动广播不是向发送者发送的逐次确认。

`scripts/agent_wow_position.py` 的 landing_evidence 要求自身对象的 movement 序号超过移动前序号。因此“必须等到新的自身对象移动更新”不能作为该协议所有正常移动的通用成功条件。这不是Python与Lua的语言问题，而是观测契约与协议语义不匹配。

对 p3_batch01_unit1 的原始包离线重放：无解码错误，自身 movement 仅序号3的创建对象，之后没有新自身 movement。目标提交位置与旧登录位置不同，approach=unknown，logout=closed。该trace为选定消息子流且 capture_complete=false，不能证明服务端没有移动，也不能证明完整网络中没有其他纠正消息。

## 修复路线（尚未实现）

位置证据应分为：

1. 登录/对象更新得到的服务端观测位置：记录会话、地图、时间与序号，不因轮询而刷新。
2. 已发送路径形成的预测位置：明确标为预测，不冒充服务器确认；请求回复只证明提交。
3. 服务端纠正/传送：需完整检查订阅与解析覆盖，收到后使旧预测失效。
4. 后续独立登录得到的边界验证：可核对最终保存位置，不代表运行中的即时确认。

下一实现工作包：先做纯函数位置证据模型与回放测试，再接入后端的当前位置字段。规则应保留来源、新鲜度、失效原因，并区分“可以用于估计下一动作”和“可宣告任务成功”。未实现/验证纠正消息覆盖前，不将预测直接当 confirmed。

实时执行中如采用预测位置接近目标，任务验收仍需服务端可观察的行为结果（例如实际命中、目标生命变化）确认，而不是仅发送攻击请求；跨地图、会话变化、死亡和纠正须使预测失效。这是拟议策略，不是已通过验证的行为。

选择本路线的原因：避免每移动一步就重登，也避免把本地服务端调试接口当作最终产品依赖。若无法取得足够的纠正/效果证据，保留明确暂停，不反复轮询或重发移动。

## 位置模型实现补充

新增 `scripts/agent_wow_position_model.py`：独立纯函数式状态模型，保留observed与predicted两类证据，携带身份（会话/角色/地图）、序号、时间、来源和动作ID。提交预测不会改变观测坐标，也不会产生position_confirmed。重复旧序号不会刷新时间。新纠正/传送观测清除旧预测；死亡或身份变化使模型失效，须重建。过期数据不可用于估计。

`scripts/test_agent_wow_position_model.py` 七项测试通过，包括基于本批次真实归档值的缓存位置验证，以及合成的纠正、身份变化、死亡、过期和无效数值。真实数据测试仅使用归档坐标和序号，测试时间由测试指定，不冒充实时回放。

尚未接入PureNetworkBackend或扩展协议订阅；当前执行器仍会对位置未确认返回unknown。模型中的position_confirmed仅表示当前选择是新鲜观测位置，不代表已到达某个目标。下一步应接入后端的只读上下文先验证来源标签，随后核对纠正消息覆盖，再单独决定动作策略；不能将usable_for_estimation当作任务成功条件。

## 行为效果门槛原型

新增 `agent_wow_effect_gate.py`，作为尚未接入执行器的证据函数：按目标GUID、攻击者GUID、动作前序号过滤正伤害事件；目标死亡必须为动作前序号之后的对象状态。伤害与死亡证据不等于物理到达，也不保证独占击杀归属。

测试以真实run15原始包确认正伤害，同时排除错误目标和过期事件；合成门槛检查覆盖不完整、重复尝试和非有限距离拒绝。两项测试通过。当前后端correction_coverage仍不完整，因此尝试门槛仍拒绝，未新增游戏操作、未更改P3成功条件。
