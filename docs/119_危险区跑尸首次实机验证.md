# 危险区跑尸：首次实机验证（2026-11-01）

## 为什么单独成篇

项目约定把**危险区跑尸**列为重点研究项，并明确：

> 灵魂医者属于单独恢复手段，不能替代或冒充危险区跑尸验证。

2026-11-01 我在蝎群（entry 3124 Scorpid Worker）一带连续死亡四次，
**每一次都用墓地灵魂医者复活**。这是错的用法：灵魂医者把角色放回墓地，
**完全没有回答"尸体够不够得着"这个问题**。四次死亡都在同一片区域
（距墓地约 88–91 码），恰恰就是跑尸研究要处理的场景，却被全部浪费掉了。

桥接其实早就实现了整条链路，之前没人用：

| RPC | opcode | 作用 |
|---|---|---|
| `bridge.query_corpse` | 0x216 | 服务端回报**尸体的地图与坐标** |
| `bridge.reclaim_corpse` | 0x1D2 | 在尸体处复活 |
| `bridge.release_spirit` | 0x15A | 释放灵魂回墓地 |
| `bridge.spirit_healer` | 0x21C | 墓地灵魂医者（**另一条**恢复手段） |

`agent_wow_worldstate.py` 早已能解码 `0x216` 的尸体事件
（`found` / `map` / `position_xyz` / `corpse_map`）——数据一直在，只是没人去取。

## 关键前置条件：死亡必须发生在会话内

之前四次死亡**都不在会话内**：会话在角色还活着且在战斗时被拆除，
服务端随后继续攻击直到角色死亡。抓包里 `death sequence: None`、
`corpse events: 0` —— **尸体事件从未被捕获**，因为客户端已经不在了。

所以第一次尝试（corpse01）改成**在会话内死亡并保持会话打开**，
这一步才让尸体变得可查。

## corpse02：跑尸链路走通

角色在蝎群处死亡（会话内），随后作为幽灵在墓地。

| 步骤 | 结果 |
|---|---|
| 幽灵位置 | `(-634.635, -4296.030, 40.525)` = 墓地，距墓地 **0.0 码** |
| 尸体对象 | `type_id=4`，**guid = 9**（尸体沿用角色自身 guid，靠 guid 识别，不靠猜） |
| `query_corpse` 回报 | `(-708.35, -4348.38, 49.03)`，**距墓地 90.81 码** |
| 幽灵→尸体直线距离 | **90.81 码** |
| navmesh 路线 | **16 个路点，总长 94.35 码**（比直线多 3.5 码） |
| 实际行走 | **4 个分段，无拒绝** |
| `reclaim_corpse` | **复活：54/108（50%），不再是幽灵** |
| 独立重登复核 | **HP 108/108、存活、非幽灵、非战斗** |

链路走通了，但**当时还不知道复活在哪** —— 会话内读到的位置是登录点。

## revive03：复活点的决定性判定

服务端不回广播自身位置（docs/88），所以答案是靠**新会话**给出的：
登出会保存角色的真实位置，下一次登录的位置就是它实际所在。

完整序列：**会话内死亡 → 登出 → 新会话（幽灵）→ 跑尸 → 登出 → 再新会话（读位置）**。

| 指标 | 值 |
|---|---|
| 死亡 | 会话内 ✓ |
| 幽灵会话登录位置 | `(-634.635, -4296.030, 40.525)` = 墓地 |
| 尸体位置 | `(-707.979, -4348.810, 49.211)`，距墓地 **90.78 码** |
| 桥接跟踪位置偏差 | **0.0**（新会话从幽灵位置起步） |
| 行走 | **4 段，无拒绝** |
| `reclaim_corpse` | 复活 54/108，非幽灵、非战斗 |
| **新会话登录位置** | **`(-707.979, -4348.810, 49.211)`** |
| **距尸体** | **0.0 码** |
| **距墓地** | **90.78 码** |
| 判定 | **`revived_at = corpse`** |

**结论：跑尸真的把角色带回尸体了。** 不是"顺路复活在墓地"——
新会话登录位置与尸体坐标**完全一致**，而离墓地 90.78 码。

跑完立刻沿 navmesh 路线跑开：`after_escape` = HP 94、存活、非幽灵、非战斗。

## 中途踩到的两个坑（都是机制性的）

### 坑一：死亡后必须先释放灵魂

角色死后处于"等待释放"状态，**还不是幽灵**，此时查尸体没有任何回应。
必须先发 `bridge.release_spirit`（0x15A），服务端才会把它变成墓地里的幽灵。
（corpse01 就是因此报"服务端没有回报尸体位置"。）

### 坑二：释放后桥接的跟踪位置会过期（最隐蔽的一个）

桥接校验路径时用的是**它自己跟踪的位置**（`b.position`），
而它只在**登录时**和**自己走路后**才知道新位置。
**释放灵魂把幽灵传送回墓地，服务端没有通知桥接** —— 桥接仍以为角色躺在蝎群。

结果：revive02 里第一段路径被按"从蝎群到墓地"计算，长度约 73 码，
桥接直接拒绝：`segment exceeds 15 yards or 3-yard height change`。

**修法：跑尸必须在"角色一开始就是幽灵"的新会话里做**，
这样桥接从登录时就从幽灵的真实位置起步（revive03 偏差 0.0）。
`run_corpse_run` 现在会**主动检测这个偏差**并报 `bridge_position_stale`，
而不是让调用方去猜为什么路径被拒。

## 交付

- `scripts/agent_wow_corpse_run.py`：跑尸链路的正式实现
  （释放灵魂 → 查询尸体 → 规划 navmesh 路线 → 分段行走 → 回收复活 → 立刻跑开）
- `scripts/test_corpse_run.py`：9 项守卫，锁住
  "尸体坐标只认服务端回报"、"路线只走 navmesh"、"非幽灵拒绝执行"、
  "无尸体/无路线如实上报而不是伪造"、"桥接位置过期必须被识别"、
  "整链必须发出 query/walk/reclaim"
- 测试基线：Windows **338 通过**（skip 13）/ WSL **345 通过**

## 与灵魂医者的分工（按项目约定）

| 手段 | 适用 | 不适用 |
|---|---|---|
| **跑尸**（本篇） | 尸体在可到达范围内（navmesh 可达）；需要研究"尸体够不够得着" | 尸体已过期；navmesh 不连通；角色在极远处 |
| **灵魂医者** | 任何时候都能把幽灵放回墓地；救援兜底 | **不能用来冒充跑尸验证** |

## 仍未验证

- **"再死时查询新尸体，以可行路径距离核对是否更接近墓地"** 这条纪律尚未演练：
  需要连续跑尸到同一墓地、比对每次尸体到墓地的**可行路径距离**是否递减。
- 跑尸期间的**幽灵移动是否会被敌对生物攻击**（本次全程脱战状态，无验证）。
- 跑尸成功后**立即跑开**的终点必须是已知可行走点：corpse02 用"远离尸体方向 × 1.5"
  现算终点失败（`no endpoint polygon`），revive03 改用墓地坐标作终点即成功。
