## 失败：huntD 造成角色死亡（第 5 次）

huntD 用改动后的代码跑：**接近成功**（4.84 码，已在近战范围），但：

```
fight outcome = target_left_melee   ← 3101 边打边退，退出了 5 码
fight rows = 79，HP 108 → 93
```

然后计划中断，恢复分支接手，**但没能救回来**：

| 环节 | 实际发生 |
|---|---|
| 恢复分支的结局选择 | `ending = finish_target`（目标已残血、角色尚健康 → 按共享规则选"击杀"） |
| 击杀尝试 | **`fallback_outcome = preconditions_not_met`** —— 目标已退出近战范围，`fight()` 拒绝开战 |
| 退出路径 | `requests = "observation + stop_attack + one retreat"`，但 `combat_cleared = false`，`reason = health floor reached…` |
| 结果 | **角色死亡**（HP 46 → 0） |

**根因**：**恢复分支假设目标够得着。**
共享规则按"目标残血 + 角色健康"选了"击杀"，但目标已经**退出近战**，
`fight()` 的前置条件（距离 ≤5 码）不满足 → 这一步变成空操作。
于是角色站在原地（撤离也没成功），直到被打死。

**这条是本轮新发现的机制缺口**，不是阈值问题：
**目标脱离接触（target_left_melee）之后，"击杀"这个结局不可执行，
必须退化成"撤离"。**

## 修复：可达性进入共享规则，恢复分支能追、也能撤

针对 huntD 的根因（**恢复分支假设目标够得着**）做了三处：

1. **共享规则考虑可达性**：`choose_combat_ending` 新增 `target_reachable`。
   目标不可达时**不再提供"击杀"这个结局**（它根本执行不了）。
2. **恢复分支先走过去再打**：`_finish_the_target` 先调 `_close_distance`，
   与战斗动作同一套做法。
3. **击杀不可执行时退化为撤离**：若 `_finish_the_target` 返回
   `preconditions_not_met`，立即改走撤离路线，而不是站在原地。
   **这正是 huntD 致死的那一步。**

状态机侧同步对齐：`_latched` 的两个分支（低血退出 / 目标离距）都改用同一条规则，
其中**目标离距状态按"目标已脱离接触"处理**（不可达 → 只能撤）。

## 批次尝试（b1–b4）：两个新根因，以及"死亡已修好"的证据

按 docs/52 的 P3 口径写了批次驱动器 `scripts/agent_wow_quest_batch.py`
（**一个批次最多 3 个任务单元**，docs/52 的上限；每个单元 = 一次移动单元 + 一次战斗单元，
前后各一次只读登录核对计数与角色状态，失败即停）。

### 根因一：撤离路线缓存会过期（b2_u1 致死）

撤离路线按目标缓存，但**角色在战斗中会移动**，于是缓存路线的起点不再等于角色的位置，
第一段路就超过桥接的 15 码上限 → 桥接整条拒绝（`retreat_movement_rejected`）
→ 角色没动 → 站在原地被打死（**第 6 次死亡**）。

**已修**：`escape_route()` 增加过期判定 —— 角色离路线起点超过 8 码就重新规划。
**b3 之后同一场景角色 HP 108 存活**（此前是死亡）。

### 根因二：会风筝的远程目标，位置估计是陈旧的（b3/b4 未击杀）

有界重新接近在 b3/b4 里**没有触发**，因为判定用的是目标的绝对位移；
而 3101 的位置来自 `estimated_position`（"last object update"），
对游走生物**严重滞后**。于是：

```
_close_distance: walked, distance_before = 13.18   （按陈旧位置走过去）
fight:           preconditions_not_me, 实际距离 11.77  （走过去的地方没有目标）
```

**这解释了 huntL 为什么能成、批次为什么不成**：huntL 落地时目标恰好在近战范围
（`already within reach`，距离 2.65–8.04 码），不需要走过去；
批次里目标游走得远，必须"走过去"，而走过去的坐标是陈旧的。

**剩余阻塞项**：**要打会游走的远程目标，需要目标位置的可靠实时坐标**。
当前只有 `estimated_position` 的外推，其精度不足以支撑"走到目标旁边"。
可能的做法（都还需要验证）：
刷新目标位置后再规划（服务端会更新生物位置）、
或按目标的**运动方向**外推而不是按最后一次更新。

## 决定性结论：会风筝的远程目标，本控制器**按现有契约杀不死**

这一段做了三个改动并逐个实机验证：

| 改动 | 结果 |
|---|---|
| **共享位置快照**（测一次、用两次） | ✅ **有效**：战斗从 `preconditions_not_met` 变成**真的开战**（b8/b9/b10 的 outcome 都是 `target_left_melee`，不再是拒绝开战） |
| **刷新目标对象**（`self.target` 是 `select_target` 时的快照，世界状态每次更新都替换对象） | ✅ **有效**：同一瞬间两次测量从相差 8.4 码变为一致 |
| **有界接近（接近阶段，走→测→再走，最多 3 次）** | ✅ 有效：10.72 → 0.16 码 |

**但战斗仍然以 `target_left_melee` 结束，目标每次都退出 5 码外。**

b10_u1 的实测：

```
_close_distance: 距离 4.17 码（已在近战范围）
fight:           开战 → 目标退出 5 码外 → target_left_melee
recovery:        撤离无效（怪会跟着走）→ 角色第 8 次死亡
```

**所以真正的原因不是位置精度、也不是快照一致性**（那两个都已修好并验证）：

> **3101（Vile Familiar）是会风筝的远程施法者。**
> `fight()` 的契约是"**近战 ≤5 码才开战**"，且"**逃跑的目标不追、也不自动重启**"
> （`test_flee_stops_without_restart`）。于是：怪一退出 5 码 → 契约要求停止这次尝试 →
> 而怪一直在近战范围内被攻击时反而会靠近（huntL 正是这样成功的：69 条采样、目标被打死）。

**结论：huntL 的成功有运气成分** —— 目标当时恰好留在近战范围内。
按现有契约，**会风筝的远程目标是打不死的**，这不是参数问题。

### 这一段还纠正了我自己两个错误判断

## 查上游得到的权威脱战机制（不再靠试错）

本机 AzerothCore 源码给出了**明确的判定**，而不是经验值：

| 事实 | 位置 | 值 |
|---|---|---|
| 脱战（leash）半径 | `src/server/game/World/WorldConfig.cpp`，`CONFIG_CREATURE_LEASH_RADIUS`（"CreatureLeashRadius"） | **30 码** |
| leash 计时器 | `src/server/game/Entities/Creature/Creature.cpp`，`Creature::GetLeashTimer()` | **11 秒**（1–5 级怪） |
| 判定对象 | 同上，`Creature::CanCreatureAttack()` | 比较 **`m_homePosition`（出生点）**，不是怪当前所在位置 |
| 伤害豁免 | 同上 | `// pussywizard: don't check distance to home position if recently damaged (allow kiting away from spawnpoint!)` —— **刚被打过的怪不判 leash** |

**所以权威的脱战配方是：**

> 1. **停止攻击**（否则 leash 计时器一直被续期，注释里明写"允许带伤风筝离开出生点"）；
> 2. 走到**距怪的出生点 > 30 码**；
> 3. **距最后一次伤害 ≥ 11 秒** —— 之后怪重置、战斗解除。

**这解释了我之前所有的失败**：
- 我的撤离路线是"离怪**当前**位置 45 码"，而 leash 判定看的是**出生点** —— 方向就错了；
- 我的等待时间是 `12 秒/30 码`（40 码 → 16 秒），**不一定盖得住 11 秒的计时器**（而且计时器是从最后一次伤害算起）。

**已按上游事实实装**：
- `LEASH_RADIUS_YARDS = 30.0` / `LEASH_TIMER_SECONDS = 11.0`（写进代码常量，注明出处）；
- 撤离路线改为**以怪的出生点为锚**（`movement.position_xyzo`，实测是静态可靠字段），
  终点放在**离出生点 > 40 码**（leash 30 + 余量 10）；
- 撤离等待改为 `走完路所需时间 + 11 秒 leash 计时器 + 5 秒余量`。

## 已把 leash 判定写进证据（不再靠命试）

撤离证据现在记录**实际落点**（而不是计划终点）与 leash 判定：

```json
"leash_verdict": {
  "actual_end": [...],                     ← 桥接自报的实际落点
  "actual_end_distance_from_hostile_spawn": ...,   ← 离出生点多远
  "beyond_leash_radius": true/false,       ← 是否越过 30 码
  "waited_past_leash_timer": true/false,   ← 等待是否盖住 11 秒
  "wait_seconds": ..., "route_length": ...
}
```

这样"撤离没解除战斗"这句话就能被拆成**是距离不够还是时间不够**，
不必再用一次角色死亡去换这个信息。

**b15**：本轮角色**存活**（HP 108，安全），但那次战斗结束时已不在战斗中，
所以没有触发撤离，`leash_verdict` 为空 —— **判定数据仍未采到**，
需要一次"战斗未决 → 触发撤离"的运行才能读到。
