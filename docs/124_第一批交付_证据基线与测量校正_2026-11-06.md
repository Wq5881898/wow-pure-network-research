## 4. 修复：退出链路把"未知"当"已脱战"

**这是本轮修掉的真实逻辑缺口 ✓**（不是风格问题 ✓）：

| 位置 | 原写法 | 后果 |
|---|---|---|
| `agent_wow_exit_recovery.py` | `observation.in_combat is not True` | **未知(None) ⇒ 报告成"已脱战" ✓** |
| `agent_wow_exit_recovery.py::close_session` | `in_combat is True` 才拦登出 | **未知 ⇒ 直接登出并拆会话 ✓** |
| `agent_wow_escape_control.py::retreat` | `me['in_combat'] is False` | **第一个 False 就结束等待 ✓**（单次采样 ✓） |
| `agent_wow_session.py::_do_recover_combat` | `in_combat is not True` | **未知 ⇒ 报告成"已清 ✓"** |
| `agent_wow_session.py::close` | 只在 `in_combat is True` 时拒绝拆除 | **未知 ⇒ 照样拆除 ✓** |
| `agent_wow_travel.py` | `in_combat is True` 才触发恢复 | **未知 ⇒ 继续走 ✓** |

**⇒ 修法 ✓**：把"战斗结束了"的判据抽成**唯一实现** ✓
（`agent_wow_combat_state_machine.OutOfCombatConfirmator` ✓），
**连续 3 次 + 2 秒驻留 ✓**，未知/未下发生命/死亡/生命下降**一律打断** ✓；
状态机、退出分支、撤离等待**共用它** ✓（撤离过程自己采到的样本**回灌**给退出分支 ✓，不再重复采样 ✓）。

**⇒ ⇒ 一个重要的行为区分 ✓**（本次修复的关键设计 ✓）：

- **报告成功** ⇒ 需要确认（3 次 + 2 秒）✓；
- **停止行动** ⇒ **不等确认** ✓ —— 服务器一说 `in_combat is False`，退出分支就**不再开新战** ✓
  （开战是副作用，不能等）✓；
  ⇒ **"不要动手"与"可以宣布成功"是两件事 ✓**。

**⇒ ⇒ 兜底也补上了 ✓**：`close(force=False)` 现在对**未知状态**同样拒绝拆除 ✓
（并记录 `close_refused` / `close_forced_unknown_combat` ✓）；
`close_session` 对未知状态返回 `status='combat_state_unknown'` ✓ 并**不登出** ✓；
旅行的**启动前置**改为要求 `in_combat is False` ✓（未知 ⇒ 不允许开始移动 ✓）。

**⇒ ⇒ 实机影响评估 ✓**：字段 59（`UNIT_FLAG_IN_COMBAT`）在归档语料里 **1508/1508 都会随建对象下发** ✓
⇒ **未知状态在实机中极少见 ✓**，本次是**堵住潜在路径**而非修复已发生的错误 ✓
⇒ **既有实机结论不因此推翻 ✓**。
