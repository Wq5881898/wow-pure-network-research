# 脱离战斗机制：从 46 个历史会话实测得出的结论

> **⚠ 本文档的结论已被实机测量推翻，请以 `docs/118` 为准。**
> 本文档基于存档离线重放得出"停止攻击 → 等 1～3 秒 → 仇恨失效 → 可登出"。随后的**实机测量（esc003）证明这是错的**：目标持续攻击时，停止攻击**不会**让仇恨失效，`in_combat` 45 秒内从未清除，角色持续掉血。档案里观察到的"1～3 秒失效"全部发生在**目标已经停手**之后。
> 保留本文档是因为它记录了**离线结论如何被实机推翻的过程**，这是本项目重要的方法论证据。正确协议见 `docs/118_脱离战斗机制实机测量与档案结论更正.md`。

本文档用存档实测回答"如何脱离战斗"，并给出可执行的脱离协议。所有数字来自 379 个存档 trace 的逐包重放，不是推断。

## 一、核心问题

2026-11-01 的死亡事故留下一个关键问题：**角色在战斗中时，怎么才能安全地脱离？**
战斗未决时断开连接会被服务端当作逃跑，角色留在世界里继续挨打至死。因此"断开连接"不是脱离手段。

## 二、实测：`in_combat` 何时被清除

对 379 个存档 trace 逐包重放，筛出**角色曾进入 `in_combat=True`** 的会话（去重后 46 个）：

| 结局 | 会话数 |
|---|---:|
| 会话内清除 `in_combat` | 32 |
| 会话结束时仍在战斗中 | 14 |

### 清除延迟（以最后一次受伤为起点）

| 指标 | 值 |
|---|---|
| 样本数 | 20 |
| 最小 | 0.10 s |
| **中位数** | **1.34 s** |
| 最大 | 2.98 s |

**清除几乎立即发生**——不是"等仇恨衰减"那种分钟级过程。

### 谁清除了战斗？两种机制

| 机制 | 会话数 |
|---|---:|
| **攻击者死亡**（击杀清除战斗） | 26 |
| **攻击者存活**，仇恨自行失效 | 11（含重复计数，去重后 2 个明确样本） |

两个机制都能清除战斗：
- **击杀清除**：目标死亡 → 战斗立即结束。26 个会话走这条路。
- **仇恨自行失效**：目标存活但不再攻击，`in_combat` 在最后一次受伤后 **1～3 秒**内被清除。

### 角色需要移动吗？**不需要。**

32 个成功清除的会话中，**角色全程位置不变（0 个移动）**。脱离战斗**不需要跑位**。

### 那 14 个未清除的会话为什么没清除？

| 会话 | 最后受伤后可用时间 |
|---|---:|
| cs002（本次死亡） | 3.09 s |
| quest792_window_long03_reconcile | 2.36 s |
| run45_quest788_controlled | 1.19 s |
| run17_attack_stop | 1.19 s |
| run53_defend | 0.91 s |
| quest792_long01_unit1_verify | 0.54 s |
| run51_retreat_combat | 0.22 s |
| run15_attack | 0.20 s |
| run22_face_attack_stop | 0.03 s |
| run21_face_attack / run52_state | 0.00 s |

**中位数 0.54 秒**，全部 < 3.1 秒。

**结论**：这些会话不是"战斗中无法脱离"，而是**在仇恨失效前就被拆掉了会话**。cs002 有 3.09 秒可用时间——比成功会话的中位数（1.34 秒）还长——但会话在那一刻被强制拆除。

## 三、脱离战斗的机制（本轮实测确认）

```
1. 停止攻击（bridge.stop_attack）
2. 目标不再攻击我 → 伤害停止
3. 服务端仇恨在最后一次受伤后 1～3 秒内失效 → in_combat 变 False
4. 此时登出才被服务端接受
```

三个已验证事实支撑这个机制：

1. **停止攻击后伤害立刻停止**：cs002 中 `fight()` 在目标逃跑后于 `finally` 发出 `stop_attack`，之后伤害停止（最后一次受伤 ms=23422，会话结束 ms=26513 期间无新伤害）。
2. **停止攻击不是清除战斗的手段**：`docs/34` 已确认 `AttackStop` 只停止本角色自动攻击，不清除敌方仇恨。实测一致——`in_combat` 在最后一次受伤后仍保持 True 约 1～3 秒。
3. **等待是有效的**：11 个"攻击者存活"样本证明，在不移动、不再攻击的情况下，`in_combat` 会在 1～3 秒内自行清除。

### 关键区分：主动逃跑 vs 被动脱离

- **主动逃跑**（`docs/34` 记录的"退出被拒，后强制结束"）：战斗中主动登出 → **服务端拒绝**，角色留在世界继续挨打 → 死亡。**这是 cs002 的死法。**
- **被动脱离**：停止攻击 → 等仇恨失效 → `in_combat` 变 False → 再登出 → **服务端接受**。run113 证明了这条路径：最后受伤 ms=22615，战斗清除 ms=22638，间隔 **0.02 秒**。

## 四、可执行的脱离协议

```
停止攻击（不重发、不追打）
  ↓
轮询观测，最多等 N 秒（N 应 ≥ 5 秒，覆盖实测最大 2.98 秒并留余量）
  ↓
in_combat 变 False  → 正常登出
  ↓
若超时仍未清除 → 说明目标仍在攻击 → 升级处理（见下）
```

**升级处理**（超时未清除时的选择，按优先级）：
1. 继续观察并重新评估血量——角色仍存活，仍有时间。
2. 若血量已低，**不得**再次主动攻击（会刷新仇恨），应保持静止等待。
3. **绝不在 `in_combat=True` 时强制拆除会话**——那正是 cs002 的死法。

## 五、落到代码：`agent_wow_exit_recovery.py`

本轮已实装的 `resolve_combat_before_exit()` 正是这个协议：

- **只观测，不攻击、不移动、不拾取**（未决战斗绝不能再开第二场）。
- 默认预算 **60 秒**，覆盖实测最大 2.98 秒两个数量级。
- `close_session()` 在角色存活但仍在战斗时先调用它，再登出；已死/幽灵则不登出并如实记录。

**与旧路径的对比**（同一脚本化后端，状态与事故一致：HP 71、在战斗中）：

| | 修复前 | 修复后 |
|---|---|---|
| 登出尝试 | **无** | 有，且是最后一个请求 |
| 请求序列 | `['observe']` | `['observe','observe','observe','execute:logout']` |

## 六、仍未确认的边界

1. **实测样本全部是"目标已停止攻击"的情形**。若目标持续追击不停（cs002 之后是否回追未观测到），仇恨失效时间可能远超 2.98 秒。60 秒预算是工程余量，不是实测上限。
2. **未实机验证"停止攻击后仇恨在 1～3 秒内失效"**。目前该结论来自存档重放（11 个样本），尚未在真实服务器上主动验证过。
3. **目标逃跑后的追击行为未知**：`Flee For Assist` 之后目标是否回头继续攻击，会直接决定脱离是"等 3 秒"还是"必须跑位"。
4. **`in_combat` 清除的服务端条件未读源码确认**。本轮只做了黑盒实测。

## 七、下一步（按价值排序）

1. **实机验证脱离协议**：在受控战斗中停止攻击后计时 `in_combat` 清除延迟，验证 1～3 秒结论，并观察逃跑目标是否回追。这是当前最大的未验证项。
2. **把脱离协议接入 `settle`**：目前 `settle()` 排在 `fight` 之后，`fight` 未决即被跳过。正确结构应是"战斗未决"独立触发脱离分支，而不是依赖 `settle` 的位置。
3. **强制接入的前提**：状态机目前只产出建议。若要强制执行，其"脱离战斗"决策必须与本协议一致——**停止攻击 + 等待**，而非主动逃跑。
