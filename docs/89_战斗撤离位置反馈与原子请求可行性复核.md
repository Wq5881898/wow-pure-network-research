# 战斗撤离：自身位置反馈与原子请求可行性复核

## 目标和范围

只读核对本机 AzerothCore 移动实现、本项目桥接接口及既有六段撤离证据。没有登录、移动、战斗或更改服务器；没有放宽 `agent_wow_retreat.execute()` 的位置证据条件。此文将“可提交请求”“游戏实际到位”和“持续脱战”分开。

## 可核实的协议与桥接事实

- 本机 `MovementHandler.cpp:379–395` 读取客户端移动信息，处理后调用 `mover->SendMessageToSet(&data, _player)`；该发送不向当前玩家会话回传同一移动包。docs/63 与旧包样本也记录了本工程的自身位置不回显现象。这不能排除所有未经检验的其他协议反馈，但当前没有可用的战斗中自身坐标确认通道。
- `probes/AgentWowBridge/actions.go:39–74` 中 `FollowPath` 仅从桥接器维护的 `b.position` 开始，以时间驱动发送移动包，再返回本地 `SubmittedPosition` 与 `ElapsedMs`。这是桥接器提交值，**不是**服务端确认玩家抵达的包。`b.positioned=true` 同样不是实际落点确认。
- `actions.go:17–29` 对每个请求限制 1..128 点、单点水平跨度 <=15 码/高差 <=3 码，总水平长度 0.05..50 码；跑步名义速度 7 码/秒只用于控制器时间计算，不是服务端位置实测。
- `module.proto:9–11,43` 的 `StepResponse` 只有 `submitted_position` 和 `elapsed_ms`，没有服务端坐标或到位证据字段。

## 已归档撤离路线的单次请求预算

`scripts/audit_retreat_atomicity.py` 只读载入已验收的 `height_R792_segment1–6_plan/reconciled.json`，结果在 `results/pure_network/retreat_atomicity_audit01.json`：

| 指标 | 值 |
| --- | ---: |
| 六段水平长度合计 | 107.034281 码 |
| 六段原样连接后的路径点数 | 218 |
| 桥接器单次上限 | 50 码、128 点 |
| 仅按距离推算的请求次数下界 | 3 次 |
| 仅按名义跑速计算的移动时间下界 | 15.29 秒 |

去程实测六段三维总长约 108.32 码；与此处 107.03 码水平长度口径不同。15.29 秒不含请求、解析、网络、目标追击及掉血处理时间，不是预计安全撤离时间。即使简化路径点数，也不能消除原样路线超过 50 码的事实；简化后的新路线还要独立验证贴地和走廊约束。

## 验收与下一步决策

本轮 Windows 全量 112 项通过（其中仅在 WSL 提供 `ip route` 的后端契约测试跳过 1 项）；WSL 全量 112 项通过、无跳过。新增两项预算测试覆盖“路径长度超限”和“点数超限分别阻止单次请求”，但测试只是桥接容量审计，不证明战斗中移动成功。

**现在的结论**：现有六段路线不能用当前 `FollowPath` 单次原样发送；拆成多次请求又缺少每次之后可信的自身位置回显，不能把 `submittedPosition` 当作下一段确认起点。现有撤离接口因此保持未接入实机，不启动新战斗来试错。

后续可分别研究两条明确任务，不先选定其一为成功方案：

1. 查证是否存在合规、独立、足够及时的游戏协议自身位置反馈，定义与登录坐标、桥接器估计值的区别；必须在离线包及有限实机实验中验证，不能只靠方法名或服务端源码推断。
2. 设计一次有上限的桥接移动请求，包括路径点、时长、取消、期间生命/战斗反馈与失败后的未知效果协议；需要重新验证其服务端到位和异常恢复。改变桥接器容量限制本身不构成安全闭环。

如果两条都无法建立证据，就保持阶段二战斗撤离分支未验收，优先做纯离线工作或重新选安全战斗场景。定时半小时巡检不能处理战斗中的秒级伤害。
