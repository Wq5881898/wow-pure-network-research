## 三、根因分析

死亡链条由三个独立缺陷叠加而成，**任何一个单独存在都不会致死**：

### 缺陷 1：退出路径在"角色存活但仍在战斗中"时放弃登出

修复前 `wsl_task_runner.py` 的退出逻辑：

```python
observation = backend.observe()
if alive(observation):        # alive() 要求 in_combat is False
    report['finalize'] = backend.execute(Action('logout', ...))
else:
    report['finalize'] = {'status': 'unresolved', 'reason': 'not alive and out of combat'}
```

`alive()` 的定义是 `health > 0 and not ghost and in_combat is False`。角色 HP 71、存活、非幽灵，**只因仍在战斗中**就落入 else 分支：**不尝试登出**。随后 `finally` 中 `backend.close()` 强制终止桥接进程与转发服务，角色带着 `in_combat=True` 留在服务端世界里。

**这是唯一直接致死的缺陷。**

### 缺陷 2：执行器在 `unknown` 后中断计划，`settle` 从未运行

`agent_wow_contract.py` 的执行循环在动作结果非 `success` 时 `break`。对有副作用的动作，`unknown` 的判定本身是**正确且必须保守**的（副作用状态未知时不得继续链式动作）。但计划里 `settle` 的位置在 `fight` **之后**，于是这个本应承担"等待脱战"职责的恢复分支被一并跳过。

单看执行器，它的行为没错；错的是**计划把唯一的脱战恢复分支放在了会被中断的位置**。

### 缺陷 3：目标逃跑使 `fight` 返回非 `target_dead`

`entry 3101` 的 SmartAI 含 `0–15% 生命 Flee For Assist`，目标在 5/83 HP 时逃跑，`fight()` 判定 `target_left_melee` 并停止攻击。这是**正确的游戏行为**，但它使 `fight` 的后置条件（`outcome == 'target_dead'`）不成立，从而触发缺陷 2。

`docs/76` 早已记录该脚本规则，本轮实证再次确认：目标 83→5 HP 后逃跑。

## 四、修复

新增 `scripts/agent_wow_exit_recovery.py`，并接入 `wsl_task_runner.py` 的**正常路径与异常路径**两处退出分支：

```python
def resolve_combat_before_exit(backend, *, budget_seconds=60, ...):
    """等待服务端清除战斗状态；只发观测请求，绝不重新交战。"""
```

- **只观测，不攻击**：恢复分支不发攻击、不拾取、不移动。上一场战斗未决时绝不能再开第二场。
- `close_session()`：存活但仍在战斗 → 先观测等待脱战 → 再登出；已死或幽灵 → 不登出，如实记录。
- 登出被服务端拒绝时**如实记录** `logout_note`，不谎报干净关闭。

修复前后对照（同一脚本化后端，状态与事故一致：HP 71、在战斗中）：

| | 修复前 | 修复后 |
|---|---|---|
| 登出尝试 | **无** | 有，且是最后一个请求 |
| 请求序列 | `['observe']` | `['observe','observe','observe','execute:logout']` |
| 结果 | 活着的角色被遗弃在战斗中 | 观测到脱战后干净登出 |

## 五、回归守卫

`scripts/test_exit_recovery.py`（7 项，全部通过）锁定的规则：

1. `living()` 只看 HP 与 ghost，**不看战斗状态**；
2. 恢复分支**只**发观测请求；
3. 战斗未在预算内清除时**如实报告**未清除，不假装成功；
4. 脱战后才登出，且登出是**最后一个**请求；
5. 已死/幽灵角色**不**登出；
6. 登出被拒时**记录**而非谎报。

全量回归：Windows **304 通过 / skipped=12**，WSL **304 通过**（修复前 297）。基线 225 项既有测试断言零删改。

## 七、遗留问题与后续

1. **`settle` 的位置仍是结构性问题**：本轮未改执行器，计划顺序仍是 `verify_alive → select_target → approach → fight → settle → logout`。本轮修复的是**退出路径**（最后一道防线），使任何原因导致 `settle` 未执行都不会致死；但 `settle` 本身仍应承担更早的脱战职责。后续应把"战斗未决"提升为独立的恢复分支，而非依赖 `settle` 排在 `fight` 之后。
2. **`fight` 的后置条件与"目标逃跑"语义**：目标是逃跑而非被击杀，`target_left_melee` 与 `target_dead` 都应视为"战斗已脱离"，需要时区分为"已脱战"与"目标已死"两种终态。
3. **强制接入仍未启用**：状态机仍是建议式。缺陷 1 的修复说明**退出路径的兜底比状态机更关键**——状态机即使强制执行，也必须由退出路径兜底。
4. **本轮实机仍无任务信用**：目标 83→5 HP 逃跑，quest 792 保持 0/8，未产生击杀。
