## 一、更正一：2026-11-01 那次跑尸用了几何更差的做法

2026-11-01 我在蝎群一带连续死亡四次，**每一次都用墓地灵魂医者复活**，
并据此以为"跑尸"尚未验证，于是另写了一套实现（`agent_wow_corpse_run.py`）。
重读 `docs/51` 之后确认这是错的：

| | 既有设计（`agent_wow_recovery_plan.py`） | 我 2026-11-01 写的 |
|---|---|---|
| 回收点 | 沿尸体→墓地路径**朝墓地推进**，但保持在尸体 **32 码**内（服务端 `CORPSE_RECLAIM_RADIUS=39`，留余量） | 走到**尸体正上方**回收 |
| 实际行走 | 约 **31.6 码**（docs/41 run42） | **90.8 码**，穿过蝎群 |
| 复活位置 | 距尸体 14.39 码，**已在朝墓地的路上** | **在敌群中央**（距墓地 90.78 码） |
| 回收后 | 立即沿已规划路径跑向墓地，**不插 sleep** | `sleep(2.0)` 后才动 |

既有设计严格更优：**服务端回收半径 39 码，根本不需要走到尸体**，
而多走 60 码就是多在敌群里待 60 码。

`docs/43` 还记着同一机制的失败样本：run47 走了 31.56 码但仍距尸体 42.5 码，
**超出回收半径 → 回收请求已写入但 ghost 未清除**，"run 的 PASS 只是会话正常退出"。

**处置**：2026-11-01 另写的 `agent_wow_corpse_run.py` 与 `test_corpse_run.py`
**已删除**，三个有价值的新发现折进既有的 `agent_wow_recovery_plan.py` /
`agent_wow_recovery_control.py`。

## 二、2026-11-01 补充的三个实机事实

这三个是既有文档里没有的，已折进既有模块并加了守卫。

### 事实一：尸体对象沿用角色自身的 guid

可见对象里 `type_id=4` 的那个，**guid 就是角色自己的 guid（9）**。
因此尸体**靠 guid 识别，不靠猜值** —— 这与 `docs/41` 的记载一致
（服务端 handler 实际从玩家自身查尸体，GUID 参数不能当回收权属验证）。

新增 `agent_wow_recovery_plan.corpse_guid()`。

### 事实二：死亡后必须先释放灵魂才会成为幽灵

角色死后处于"等待释放"状态，**还不是幽灵**，此时查尸体**没有任何回应**
（corpse01 因此报"服务端没有回报尸体位置"）。
必须先发 `bridge.release_spirit`（0x15A）。

新增 `agent_wow_recovery_control.release_if_dead()`。

### 事实三（最隐蔽）：释放后桥接的跟踪位置会过期

桥接校验路径时用的是**它自己跟踪的位置**（`b.position`），而它只在
**登录时**和**自己走路后**才知道新位置。
**释放灵魂把幽灵传送回墓地，服务端没有通知桥接** —— 桥接仍以为角色躺在蝎群。

结果：第一段路径被按"从蝎群到墓地"计算（约 73 码），桥接直接拒绝：

```
segment exceeds 15 yards or 3-yard height change
```

**修法：跑尸必须在"角色一开始就是幽灵"的新会话里做**，
这样桥接从登录时就从幽灵的真实位置起步（实测偏差 0.0 码）。

新增 `agent_wow_recovery_plan.bridge_position_is_stale()`。

## 三、复活点的判定方法（补上 docs/41/43 未做的部分）

服务端不回广播自身位置（docs/88），所以会话内读到的位置是登录点。
判定办法是**登出再重登**：登出会保存角色的真实位置，下一次登录的位置就是它。

revive03（用更差的几何，仅作方法验证）：

| 指标 | 值 |
|---|---|
| 尸体位置 | `(-707.979, -4348.810, 49.211)`，距墓地 90.78 码 |
| **新会话登录位置** | **`(-707.979, -4348.810, 49.211)`** —— 与尸体**完全一致** |
| 距尸体 / 距墓地 | **0.0 码** / 90.78 码 |

**这条方法本身要保留**：它是唯一能在不依赖服务端回显的前提下判定复活点的手段。
但**几何必须换成既有设计的"朝墓地推进 32 码前缀"**。

### 接入时补上的一环：第一段路

既有控制器从**回收点**开始，回收点之前的路没人走。而实际几何是：

- 幽灵出现在**墓地**；
- 尸体在**敌群**里（本次距墓地 85.01 码）；
- 服务端 `CORPSE_RECLAIM_RADIUS=39`，**幽灵必须进入尸体 39 码内**才能回收。

所以第一段路是**从墓地沿同一路径反向走到回收点**。
第一次接入时我把它接成了"从尸体到回收点"，桥接按"从尸体起算"校验第一段，
直接拒绝：`segment exceeds 15 yards or 3-yard height change`。

**修法**：`select_recovery` 增加 `approach_chunks` = 剩余路径的**反向**分段。

| 阶段 | 结果 |

**这次是真正的"跑尸"**：不是复活在尸体旁，而是**复活在尸体与墓地之间、

### 三个必须守住的判据

1. **会话正常退出 ≠ 复活成功**（docs/43 run47 的教训）。
   本次显式核对 `ghost_cleared`（HP>0 且 ghost=false），并用**新会话**核对位置。
2. **回收确认后不插 sleep**，立即发首段跑步。
3. **桥接位置过期必须先被识别**：释放会把幽灵传送回墓地却不通知桥接，
   桥接仍按尸体处的位置校验路径 → 必须从"角色一开始就是幽灵"的新会话起步。
